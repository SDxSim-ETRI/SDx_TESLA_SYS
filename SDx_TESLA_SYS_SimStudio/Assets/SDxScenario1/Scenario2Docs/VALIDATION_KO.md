# 상황2 검증 기록 — SDx Scenario 2 v1.0

## 모델과 검증 환경

- 원본: 사용자가 업로드한 SDx_TESLA_SYS_SimStudio.tar.gz (MainScene 기준) 및 이후 정상 동작한 상황1/카메라 패키지.
- 모델: 저장된 Scene의 World, 로봇, 책장, 책, 새 미닫이문 배치와 사용자가 지정한 상황1 시작 위치를 재구성.
- 물리: 사용자 프로젝트에 포함된 libmujoco.so를 실제 로드. mj_versionString 반환값 3.16.0.
- 시간 간격: 0.001초.
- 두 문의 qpos: 상황2 리셋은 각각 0m, 상황1 리셋은 각각 2.4m.
- Unity에서 최종 생성한 런타임 XML이 아니라 재구성한 모델이라는 한계가 있습니다.
- 네이티브 시험은 Python/C 테스트 하네스로 제어했으며, Unity C# 코드를 직접 실행한 시험은 아닙니다.
- 긴 시험은 전체 적분 상태(위치/속도/시간/워밍스타트/입력 등)와 제어기 상태를 저장/복원하는 구간 실행으로 수행했습니다.

|---|---:|---:|---:|
| 전체 작업 완료 | 통과 | 통과 | 통과 |
| 책 중심 목표 오차 | 1.061mm | 1.061mm | 1.055mm |

시뮬레이션 시간은 물리 모델 안의 시간이며 PC 실행 시간이나 제작 소요 시간 예측이 아닙니다. 두 상황2 반복은 같은 상태로 리셋한 결정론적 조건입니다. 다양한 시작 오차에 대한 강건성 시험이 아닙니다.

최종 상황2 책 중심(네이티브 X,Y,Z):
`(5.228945072174319, -4.500112716139022, 0.9243414347100838)`m

Unity X,Y,Z:
`(5.228945072174319, 0.9243414347100838, -4.500112716139022)`m

책을 놓고 양팔을 복귀한 후 추가 5초의 시뮬레이션 시간을 관찰한 결과입니다.

문 최대 설정은 2.4m이며, 접촉으로 당긴 최종 위치는 약 2.387m였습니다. 설정 상한까지 남은 거리는 약 12.6mm이고, 그 상태로 출입구를 통과했습니다. 정확히 2.4로 강제 지정한 결과가 아닙니다.

## 실제 접촉과 관절 구동

책의 자유 관절을 유지하고 왼쪽 손가락과 책의 접촉력을 이용했습니다. 오른쪽 손가락과 001 문 앞 손잡이의 접촉 기록도 저장했습니다. 오른팔 자세를 유지한 채 본체의 바퀴를 구동하면 손잡이를 통해 수동 문이 움직입니다.

문 Actuator, 문/책 용접 제약, 런타임 Transform 재배치, 외부 본체 wrench, 운반 중 qpos 강제 쓰기는 사용하지 않았습니다.

접촉 표본은 대략 1초 간격이며, 구간 경계에 따라 간격은 조금 달라집니다. 매 1ms 모든 접촉을 별도로 사후 감사한 검사는 아닙니다. 다음 접촉은 허용했습니다:
- 바퀴와 바닥
- 왼쪽 그리퍼 손가락과 대상 책
- 오른쪽 그리퍼 손가락과 문001의 앞 손잡이 막대
- 초기 대상 책과 테이블
- 목표 책과 왼쪽 책장의 선반

기존 World의 충돌 설정을 유지했으므로, 렌더링되는 모든 벽에 충돌이 켜졌다는 뜻은 아닙니다. HouseWallB의 기존 0/0 마스크는 유지했습니다.

## 추가 검사

- 손잡이를 잡은 중간 상태에서 리셋하여 두 문 닫힘, 로봇/책/관절 초기화, qvel=0, ctrl=0, 시간=0 확인.
- Unity처럼 문짝 시작 Transform이 열린 위치이고 joint ref가 2.4인 경우에도 qpos=0 리셋이 동일한 닫힌 상태를 만드는지 확인. 손잡이 위치 차이 약 4.93e-16m.
- 오른손 목표 방향의 좌표축 변환과 250회 반복 한도 IK 수렴 확인.
- 기존 상황1의 관절 궤적 데이터, 경유점 배열과 배치 단계 코드 보존 확인.
- 기존 int/ulong 수정 유지 및 새 네이티브 카운트 혼합 연산 유무 점검.
- 단일 제어기만 Actuator를 갱신하고 새 코드가 mj_step을 중복 호출하지 않는지 점검.
- 설치 파일 검증, 외부 백업, .meta 보존, 재설치, 사용자 코드 불일치 시 중단, 복원 절차 검사.
- 카메라 파일 변경은 상황2 명령에도 리셋 시점 보간 초기화를 요청하는 조건 추가뿐입니다.

## 미검증

- Unity Editor에서 C# 컴파일.
- 사용자 PC의 최종 Scene에서 GUI 입력부터 완료까지의 전체 Play 실행.
- 변경된 가구 배치, 다른 문 손잡이/레일 방향/마찰에서의 성공.
- 모든 순간에 대한 연속 충돌·간섭 인증.
- 실제 로봇 하드웨어.

따라서 네이티브 시험 성공을 Unity 통합 실행 성공으로 표현하지 않습니다. 기존 상황1이 사용자 환경에서 정상 동작했다는 확인은 유지하되, 새 문 조작 C# 연결부는 적용 후 검증이 필요합니다.
